# TourAPI 호출·저장 운영 정책

확인일: 2026-09-09 · 군번여지도 강원 · **① 웹·앱 개발 부문**

## 1. 운영 원칙

**정상 관광 기능을 유지할 트래픽을 먼저 확보한다.** 관광·문화·행사·숙박·음식점 5유형, 검색·상세·무장애를 한도에 맞추려고 축소하지 않는다. 동일 동작의 중복 처리와 실패 후 반복 재시도만 개선한다. 데이터 저장은 별도 절차에 따라 준비하며, 저장 문의가 실시간 기능이나 증설을 지연시키지 않게 한다.

현재 관광공사 응답을 운영 서버 DB에 적재하거나 정기 동기화하지 않는다. 원문 정책의 저장 절차·범위를 확인한 뒤 적용한다. 신청 제출만으로 시작할 수 있는지, 별도 회신이 필요한지는 담당자 답변 없이 확정하지 않는다. 문의·신청은 아직 발송하거나 제출하지 않았다.

## 2. 실제 관측과 오류 해석

2026-09-08 개발 환경의 오류 실측이다. **9/9 11:28 KST 고성 5유형 재조회는 전부 성공, 149개였다.** [실연동 증빙](qa/day-passport/tourapi-live.json). 성공 당시 조회가 가능했다는 뜻이며 승인량 증가나 오늘 전체 잔여량을 뜻하지 않는다.

| 요청 | 관측 | 판단 |
|---|---|---|
| `KorService2/areaBasedList2` | HTTP 429, `returnReasonCode=22` | 해당 요청의 일일 한도 초과 |
| `KorService2/ldongCode2` | 성공 | 당시 코드 조회 가능. 다른 오퍼레이션의 정상 여부는 별개 |

[공공데이터포털 공식 오류 표](https://www.data.go.kr/tcs/dss/selectErrCodePopupView.do)는 **22: 일일 요청 한도**, **23: 초당 요청 한도**로 구분한다. 23은 짧은 대기 후 재시도할 사유이지 일일 이용 중단으로 처리할 사유가 아니다. HTTP 429만으로 22를 추정하지 않고 JSON/XML의 제공자 코드를 확인한다. 20·30·31 등 인증·접근·만료 오류도 별도로 처리한다.

[콘텐츠랩 FAQ](https://api.visitkorea.or.kr/#/cmsFAQ)는 매일 00시 일일 사용량 초기화를 안내한다. 시간대·계정 적용 상태는 확인 대상으로 남기고, 기존 앱의 10분 오류 차단을 제공자 초기화 시간으로 표시하지 않는다. 실제 콘솔 승인량과 집계 단위는 미확인이다.

오류 기록에는 일시·서비스·오퍼레이션·HTTP 상태·제공자 코드·지연·재시도 여부만 남긴다. 인증키, 키가 포함된 URL, 원문 응답 전체를 공개 보고서나 사용자 오류 메시지에 넣지 않는다.

## 3. 저장 판단의 공식 근거

| 근거 | 적용할 내용 |
|---|---|
| [국문 서비스 카탈로그](https://www.data.go.kr/data/15101578/openapi.do) | 무료·데이터 이용허락 표시를 확인한다. 이것만으로 API 트래픽 또는 저장 방식이 무제한이라고 해석하지 않는다. |
| [콘텐츠랩 저작권 정책](https://api.visitkorea.or.kr/#/useServiceGuide/2) | 이용 안내 → 저작권 정책 → 출처 표기 정책 → 활용 주의사항에 로컬서버 콘텐츠 캐싱 금지가 명시돼 있다. |
| [콘텐츠랩 고객지원 FAQ](https://api.visitkorea.or.kr/#/cmsFAQ) | 실시간 이용과 서버 구축 방식을 구분하며, 서버 구축은 담당 메일로 신청자명·API명·인증키를 전달해 관련 신청서를 받는 절차를 안내한다. 검토는 최소 3–5일 이상이다. |
| [① 개발 부문 저장 FAQ](https://lowly-polyanthus-1fb.notion.site/2026-36b5dce406e380e0a3d1f80525667a11#3715dce406e380cebabbe62a3ce7b9e8) | 실시간 호출을 강력 권고하며 개발 중 실제 호출 이력이 없으면 심사상 불이익 가능성을 안내한다. 불가피한 DB 저장은 별도 신청과 `tourapi@knto.or.kr` 문의 대상이다. |

짧은 TTL·브라우저 메모리·사진 URL·사용자 일정의 일부 장소 필드가 자동 예외라는 규정은 확인하지 못했다. 현재 브라우저 페이지 메모리 재사용도 문의 범위에 포함한다. 기술 매뉴얼에 동기화 기능이 있다는 사실은 저장 신청의 면제가 아니다.

서버 구축 절차의 구체 양식·신청자 자격·허용 매체와 항목·갱신/삭제 주기·저장 시작 시점을 답변받아 기록한다. 사진은 공공누리 유형과 별도 권리 조건도 확인한다. 운영계정 전환과 데이터 저장 신청은 서로를 대신하지 않는다.

## 4. 현재 코드와 개선 상태

| 항목 | 상태 |
|---|---|
| 외부 요청 | 서버 `tourRequest`에서 `cache: no-store`와 요청 시간 제한 사용 |
| 앱 장소·상세 응답 | `Cache-Control: no-store` |
| 관광 콘텐츠 운영 DB·정기 동기화 | 미실행 |
| 서버 `provider_limits` | 서비스·메서드·키 해시 식별자와 오류코드·재시도 시각만 저장. 관광 응답·원문 키 저장 아님 |
| 페이지 응답 재사용 | `pageFetch`가 페이지 수명 동안 요청·완료 응답을 메모리 재사용. 새로고침 시 초기화되며 ‘캐싱 없음’이라고 설명하지 않음 |
| 기존 오류 차단 | 429/22 등에 10분 차단을 적용한 구조. 이 시간은 앱의 재시도 억제값 |
| 22/23 개선 | JSON/XML 22/23·인증 오류 구분, Retry-After 우선, 미제공 시 22는 10분·23/일반429는 30초 후 재요청 가능. 단위 검증 완료; 배포 증빙은 최신 전달 기록 참조 |

코드: [tour-api.ts](../web/lib/tour-api.ts), [provider-limit.ts](../web/lib/provider-limit.ts), [page-cache.ts](../web/lib/page-cache.ts). 정적 코드 상태와 공개 배포 검증은 구분한다.

## 5. 정상 이용을 보전하는 요청 제어

새 권역의 국문 조회는 코드 2회와 5유형 목록 5회다. TourAPI 장소 상세는 국문 2회·무장애 1회, 검색 페이지는 국문 3회, 권역 무장애 조회는 최대 7회다. 성공 경로의 산출과 실제 이용량을 분리해 [호출량 모델](api_capacity_model.json)로 증설 근거를 만든다.

- 추천·검색·상세·무장애의 정상 수요에 필요한 승인량을 확보한다. 자체 저한도·유형 제거·검색 제한을 운영 목표로 삼지 않는다.
- 동일한 사용자 동작의 진행 중 요청을 공유하고, 제목·시간 편집처럼 관광 정보가 바뀌지 않은 작업은 재계산한다. 완료 응답 재사용의 허용 범위는 저장 문의와 구분해 기록한다.
- 제공자 22/23·인증·일반 오류를 분리하고 복구 가능한 오류에는 적절히 재시도한다. 동일 실패의 연쇄 재시도를 막되 23 때문에 하루 내내 정상 기능을 막지 않는다.
- 공급자별 호출 수·성공률·오류·지연을 관측한다. 경보는 추가 증설 판단에 사용하며, 계정 승인값을 추정해 사용자를 차단하지 않는다.
- 자동 회귀 검사와 실제 API 검증을 구분한다. 실제 조회 실패 때 다른 출처 자료를 제공한다면 출처·시각·조회 상태를 명확히 표시한다.

## 6. 트래픽 확대 절차

[공식 FAQ](https://api.visitkorea.or.kr/#/cmsFAQ)는 운영계정 신청 기본 일 100,000건과 기존 운영계정의 운영팀 추가 증설 경로를 안내한다. **현재 우리 계정의 승인량이 10만이라는 뜻은 아니다.** 개발 호출 이력·서비스 식별·URL·내용을 갖추며, 통상 약 1주라는 검토 안내는 보장 기한이 아니다.

[공모전 신청 가이드](https://drive.google.com/file/d/1iAy4zLbWT4gWbc7PkW2mujdQBFD-2-BC/view)에 따라 실제 활용 대표 API 1개를 팀별 1회 신청한다. 국문 대표 신청을 준비하면서 국문·무장애 전체의 추가 트래픽을 어떤 경로로 적용할지 운영팀에 함께 요청한다. 별도 다중 신청을 임의로 만들지 않는다.

현재 승인량·집계 단위·사용량 확인 → 정상 기능의 수요와 피크 산출 → 대표 신청/운영팀 증설 요청 → 공모전 지원 조율 → 승인·적용량 확인 → 정상 사용자 흐름의 실연동 검증 순서로 진행한다. 세부 연락처·기본량·일정은 [실행안](api_capacity_strategy.md), 실제 제출 문안은 [신청 준비본](api_capacity_requests.md)에 모았다.

## 7. 저장 방식 신청 문의 이메일 초안 — 미발송

중복 문안을 없애고 [신청 준비본](api_capacity_requests.md)의 4절 ‘저장 방식 신청서·허용 범위 문의’를 기준으로 관리한다. 트래픽 증설 메일과 제목·질문을 분리한다.

인증키는 공식 FAQ가 요청하는 신청 항목이지만 이 문서·Git·공개 Q&A에 기록하지 않는다. 실제 정식 신청 시 담당자가 지정한 공식 비공개 경로에서만 전달한다. 저장 절차 회신을 받은 뒤 원천 ID·확인 시각·출처·이용조건과 함께 최소 항목을 보관하고 갱신·삭제·장애 복구를 설계한다. 회신 전 서버 적재·동기화 작업은 실행하지 않는다.
