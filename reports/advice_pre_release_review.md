# 공개 훈수 초안 코드 리뷰

2026-09-09 · 읽기 전용. 저장소/Git/배포/외부 관광 API 변경·호출 없음. Node 순수 함수와 메모리 SQLite로 아래 산식/SQL만 재현했다. 줄 번호는 검토 시점 코드 기준이다.

## 수정할 실제 오류

### P1. 익명 공유 읽기가 제한 없이 TourAPI 요청을 증폭한다

- 위치: `web/app/api/public-advice/[id]/route.ts:18`, `web/lib/advice-server.ts:66–68`.
- `?q=` 검색만 `adviceRateLimit`을 거친다. 기본 GET은 비로그인 누구나 반복할 수 있고, 매번 스냅샷 12개 + 제안 60개의 고유 관광 참조를 `detailCommon2`로 해석한다. 이론상 요청 1개가 최대 72개 외부 요청이 된다.
- 공개 URL을 아는 요청자가 이를 반복하면 관광 키 한도를 소모해 기존 정상 추천/검색도 실패할 수 있다. 페이지 내 상태를 읽는 기능이 공개 TourAPI 호출 프록시가 된 것이다.
- 조치: 기본 GET에도 **해석 실행 전에** 공유/방문자/엣지 단위 남용 제한·동시 중복 요청 제어를 적용한다. 정상 검색 풀을 축소하지 말고, 메타데이터 새로고침과 변하지 않은 공개 장소 해석을 구분한다. 현재 데이터 저장 정책의 범위를 넘어 서버 콘텐츠 캐시로 해결하지 않는다.

### P1. 삭제 후 재제안이 같은 ID를 재사용해 다른 제안이 채택된다

- 위치: public route `30–34`, owner route `web/app/api/advice/route.ts:30–32`.
- 제안 ID는 `hash(shareId + visitorHash)`여서 동일 방문자가 삭제하고 다시 제안하면 같은 ID다. 소유자는 ID만 보내 `adopt`하고 payload/revision을 확인하지 않는다.
- 재현: 방문자가 A 제안 → 소유자가 A를 검토/로컬 저장 → 방문자가 A 삭제 후 B 제안 → 소유자의 기존 A 채택 요청 도착 → **B가 adopted**. SQLite로 같은 SQL을 실행해 `place-B, adopted` 확인.
- 조치: 새 제안마다 무작위 ID를 발급하고 별도 클라이언트 멱등키를 둔다. 또는 제안 revision/payload 해시를 소유자 요청에 포함하고 `UPDATE … WHERE revision=?`로 비교한다. UI가 반영한 내용과 DB 채택 대상이 일치해야 한다. 수정 기능을 추가할 때도 같은 검사가 필요하다.

### P2. 다른 방문자의 신고가 작성자에게 표시되지 않는다

- 위치: `advice-server.ts:64,69`, `web/components/advice-shared.tsx:30,32`.
- 신고 조회는 `WHERE visitor_hash = 현재 세션`만 사용한다. 소유자의 `reported` 값에는 **다른 방문자가 접수한 신고가 들어오지 않는다.** 방문자 UI는 ‘작성자에게 알렸어요’라고 하지만 소유자 ‘신고 접수’ 표시는 작동하지 않는다.
- 재현: visitor-b 신고 행이 있는 상태에서 owner hash로 현재 SQL 조회 → 빈 배열.
- 조치: 소유자 응답에는 제안별 신고 존재/건수를 별도 집계한다. 일반 방문자에게는 본인 신고 여부만 제공하고 신고자 hash는 공개하지 않는다.

### P2. 12곳 코스에 반영 불가능한 13번째 장소 추가 제안을 받는다

- 위치: `web/lib/advice-model.ts:24` 대 `29`.
- `validSuggestion`은 12개 스냅샷의 `add`를 허용하지만 적용 함수 `suggestionIds`는 결과 13개를 null로 거부한다. UI에도 12개일 때 추가 방식 차단이 없다.
- Node 재현 결과: `{acceptedByServerValidator:true, applicableToPlan:null}`.
- 조치: `add`는 스냅샷/적용 결과가 12개 이내인지 서버에서도 검증한다. UI는 한도에 도달하면 대체/삭제 방식으로 안내한다. 저장 시 지원하지 않는 제안을 미리 거부한다.

### P2. 만료된 공유는 소유자/제안자도 삭제할 수 없다

- 위치: `advice-server.ts:59–60`, owner route `24–27`, public route `22,40–42`.
- `findShare`가 만료되지 않은 행만 반환하는데 소유자 삭제와 제안자 철회도 같은 함수를 사용한다. 30일 후 링크가 닫히면 작성자가 자신의 DB 자료를 삭제할 경로가 사라진다. 목록도 만료 행을 제외하며 현재 공유/제안 만료 정리는 없다.
- 조치: 공개 읽기의 만료 판단과 권한 있는 관리/삭제 조회를 분리한다. 소유자/해당 제안자는 만료 후에도 삭제 가능해야 한다. 정리 정책을 별도로 구현한다면 실제 실행과 보관 기간을 함께 기록한다.

## 요청 기능의 미구현 구간

현재 방문자는 한 여행당 제안 하나를 남기고 **삭제 후 새로 작성**할 수 있다. 본인 제안 직접 수정 API/UI는 없다. 이는 위 ID 재사용 오류와 별개로, 본인 수정까지 제공할 계획이라면 update + revision 흐름이 필요하다. 지금은 직접 수정이 구현됐다고 안내하지 않는다.

## 검토 범위에서 문제로 확인하지 않은 것

- 소유자 관리는 테스트 입장과 별도 HMAC 쿠키 해시 검사를 거친다. 방문자 철회도 `visitor_hash`를 검사한다. 현재 읽은 경로에서 다른 글/제안의 권한을 ID만 바꿔 획득하는 직접 IDOR는 발견하지 못했다.
- 공개 스냅샷 저장은 region/question/placeIds로 새 객체를 만들며 관광 응답 원문·개인 시각·만남 좌표를 DB에 복사하지 않는다. `shareDetail`은 권한 hash를 제거한 제안과 제한한 장소 필드만 반환한다.
- 공개 경로 예외는 `/p/{32hex}`와 `/api/public-advice/{32hex}`에 한정돼 있다. `/api/groups`와 일반 `/api/places`는 계속 테스트 입장으로 보호된다.
- 변경 요청의 정확한 Origin·JSON·8KB 스트림 상한 검사는 적용돼 있다. 이것이 종합 침투 테스트 통과를 의미하지는 않는다.

회귀 검사 권장: 익명 기본 GET flood 제어, A 삭제/B 재제안 중 늦게 도착한 A 채택, 제3자 신고의 소유자 표시, 12곳 add 거부, 만료 후 본인 삭제, 타인의 수정/삭제 거부. UI 통합 중인 작업을 완료 기능으로 판단하지 않았다.
