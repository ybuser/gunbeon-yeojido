# 제품 완결성 검토 v3 초안

- 검토일: 2026-09-07
- 기준: ① 웹·앱 개발 부문 1차 심사용 강원 지역특화 모바일 웹. 기존 핵심 경험을 마무리하는 범위이며 새로운 서비스 확장을 제안하지 않는다.
- 읽은 자료: `reports/implementation_plan.md`, `reports/design_concept_v2.md`, `reports/proposal_review.md`, 현재 `web/lib/domain.ts`, `web/components/passport-app.tsx`.
- 방법: 기획과 소스의 정적 대조. 작성자는 브라우저·Git·Sites·하위 에이전트를 사용하지 않았고 web 코드를 수정하지 않았다. 아래 춘천 화면 사례는 루트가 실제 배포 UI에서 관찰해 전달한 내용이며 작성자가 재현한 결과는 아니다.
- 상태: 구현 결정 전 초안. 이후 수정·브라우저 검증 결과를 별도 연결해야 한다.

## 판단

지역 탐색, 시간 계산, 지도, 부모 입력, 저장·기록, 출처가 갖춰져 있다. 남은 핵심은 **고른 일정이 저장·가족 제안·다시 보기까지 같은 내용으로 이어지는가**, 그리고 **실제 장소가 미션 이름과 추천 이유를 뒷받침하는가**다. 화면을 더 늘리기보다 이 두 약속을 완성하는 편이 기능심사와 실사용 모두에 도움이 된다.

같은 브라우저의 가족 체험, 거리 기반 시간 추정, 시군 대표 격자 예보, 1박 일정 초안, 제도 준비 안내라는 한계는 이미 여러 화면과 디자인 명세에 기록되어 있다. 이 범위를 숨기거나 이번에 모두 실서비스 수준으로 확대할 필요는 없다. 다만 기능명이 실제 동작보다 넓은 기대를 만드는 부분은 아래처럼 줄여야 한다.

## 1. 저장한 일정이 같은 여행으로 남지 않는다

**현재 근거:** `domain.ts:287`의 미션 ID는 지역+유형이다. `domain.ts:432`의 Entry는 미션 ID·제목·지역·스탬프만 저장한다. `passport-app.tsx:520`의 `saveMission`은 같은 ID가 있으면 새 항목을 만들지 않는다. 다시 보기는 그 ID로 현재 조건의 후보를 재구성한다. 디자인 v2도 이 한계를 명시한다.

**실사용 문제:** 같은 철원 가족 미션을 나중에 다른 장소·동행으로 다시 계획해도 별도 여행으로 담기지 않는다. 저장 당시 카페·장소 순서를 확인할 수 없고 API 결과나 공개 거점이 바뀌면 다른 미션을 보게 된다. “현재 조건으로 다시 보기” 문구는 정직하지만, 주요 저장 기능이 여행의 연속성을 충분히 제공하지 못한다.

**이번 최소 보완:** 미션 템플릿 ID와 사용자 여행 ID를 분리한다. 허용된 공개 장소 참조 ID·순서·사용자가 선택한 체류값 등 계획에 필요한 최소값을 보존하고, 저장된 계획 보기와 현재 시각으로 다시 계산하기를 구분한다. 관광공사 원문 응답 저장 제한을 유지하며 전체 Place·이미지·상세 응답을 통째로 저장하는 방식은 피한다. 재조회하지 못한 참조는 “현재 정보를 불러오지 못함”으로 남기고 다른 장소로 조용히 바꾸지 않는다. 정확한 복귀 기준시각과 군 정보는 계속 저장하지 않는다.

**제출 전 필수:** 저장→새로고침→다시 열기에서 공개 장소 순서가 유지되고, 현재 목표시각은 새로 정해 계산됨을 실제 브라우저로 확인한다. 같은 지역·유형의 두 여행이 구분되어야 한다.

**후순위:** 계정 동기화, 다중 기기 여행 보관, 상세 변경 이력. 이번에는 로컬 계획의 일관성만 완성한다.

## 2. 부모가 제안한 내용과 자녀가 보는 내용이 달라질 수 있다

**현재 근거:** `passport-app.tsx`의 proposal은 Mission과 도보·교통값을 받는다. 그러나 내 여행의 제안 “살펴보기”는 지역·조건을 바꾸고 `proposal.mission.id`를 선택할 뿐, 부모가 제안한 실제 stops를 표시 대상으로 사용하지 않는다. `domain.ts:451`의 가족 일정 projection도 ID·제목·지역만 전달한다.

**실사용 문제:** 부모는 장소 두 곳을 제안했는데 자녀 화면은 다른 데이터·거점으로 재생성한 같은 이름의 미션일 수 있다. 부모가 자녀의 실제 장소·순서를 보지 못하고 제목만 받으면 “같이 계획한다”는 경험도 약하다. 동시에 “살펴보기”만 눌러도 자녀의 현재 조건이 바뀌므로 검토와 적용의 구분이 흐리다.

**이번 최소 보완:** 받은 제안은 당시 공개 장소 참조·순서·도보/교통 조건을 그대로 읽기 전용으로 보여준다. “이 제안으로 계획하기”에서만 현재 계획에 적용하고 새 목표시각으로 다시 평가한다. 일정 공유 권한이 있으면 공개 장소 이름·순서를 보여주되 정확한 시간·좌표·군 복귀경로는 제외한다. 제안 수락 여부 하나와 취소/닫기만 있으면 충분하며 실시간 채팅은 필요 없다.

**제출 전 필수:** 부모 제안→자녀 검토→명시적 적용→저장까지 같은 장소가 유지된다. 공유/제안 권한 해제 후에는 해당 보기·동작이 닫히고, 부모의 단순 제안이 자녀 계획을 자동 덮어쓰지 않는다.

**후순위:** 다른 기기 간 초대, 실시간 공동 편집, 계정 인증. 같은 브라우저 체험임을 계속 명시한다.

## 3. 관광 장소와 평화·호국 미션의 이름이 일치하지 않는다

**현재 근거:** `domain.ts:263`의 평화 미션은 공개 방문이 검증된 현충시설이 없으면 일반 관광 후보 또는 origin으로 대체하지만 이름과 브리핑은 계속 호국·평화로 남는다. 실내 후보는 장소명 정규식, 일반 후보는 범주·거리 중심으로 고른다. 춘천·속초에는 기본 anchors가 없다.

**루트 전달 실제 관찰:** 춘천 평화 미션에 춘천시립도서관(장난감도서관)·카페드220볼트·국립춘천박물관이, 가족 미션에는 클랑포레스트·카페·동내도서관이 나타났다. 도서관이나 박물관 자체가 부적절하다는 뜻은 아니다. 선택한 시설과 “평화/호국” 이름 사이의 근거가 화면에 없다는 문제다.

**이번 최소 보완:** 평화·호국 근거가 있는 장소를 포함할 때만 해당 이름을 쓴다. 근거가 없으면 “지역 문화 탐방”, “잠시 쉬어가는 미션”처럼 내용에 맞는 일반 이름으로 낮춘다. 춘천·속초는 확인된 공개 민간 관문 장소를 우선 제시하되 데이터가 없으면 사용자 선택을 요구한다. 미션마다 관광 목적을 설명하는 한 줄 이유를 추가한다. 예: “박물관 관람과 가까운 휴식 장소를 묶었습니다.” 장소가 같고 순서도 같은 카드는 유형 이름만 달리하여 중복 노출하지 않는다.

장소 유형에 대한 최소 제외도 필요하다. 장난감 대여시설 등 이용 자격·대상이 좁은 시설을 일반 관광 앵커로 자동 선택하지 않는다. 명칭만으로 모든 도서관을 제외하기보다 관광 목적·대상과 공개 이용 근거를 확인한 후보를 우선한다. 검증되지 않은 현충시설을 평화 미션을 채우기 위해 다시 허용하지 않는다.

**제출 전 필수:** 접경 5군마다 대표 미션 1개에서 실제 관광 목적, 동행 적합성, 지역 이야기, 공개 출입 확인 경로를 설명할 수 있어야 한다. 5군 중 확인이 부족한 권역은 후보 탐색으로 표시한다. 춘천·속초는 관문으로 유지하고 전국 여행 서비스로 넓히지 않는다.

**후순위:** 수백 개 수작업 코스, 인기 순위 학습, 관광지 집중률·연관 관광지 전체 매칭. 먼저 소수 대표 조합과 이름의 신뢰도를 확보한다.

## 4. 입력한 조건이 결과에 반영되는 범위를 더 명확히 해야 한다

**현재 근거:** 가족 방문 날짜는 제목 아래에 표시되지만 날짜별 운영/예보 검증과 연결되지 않는다. 식사 후보는 restaurant 유형의 앞 3개여서 식사 선호를 바꿔도 동일하다. 도보 상한을 넘으면 경고하지만 장소 대체·제거 기능은 없다. 디자인 v2가 이를 사실대로 설명하고 있어 숨겨진 구현 주장으로 보지는 않는다.

**실사용 문제:** 사용자는 방문 날짜·선호 식사·편한 도보 시간을 입력한 뒤 그 조건에 맞는 결과를 기대한다. 입력과 결과 사이의 약속이 실제로는 메모·경고에 그치면 “맞춤 브리핑”의 효용을 판단하기 어렵다. 특히 미래 방문일 아래 현재부터 8시간 날씨가 함께 있으면 방문일 예보로 읽힐 수 있다.

**이번 최소 보완:** 입력을 실제 판단에 쓰는 조건과 가족에게 남기는 선호 메모로 구분한다. 음식점에 검증된 메뉴 태그가 없다면 “주변 음식점 후보 · 선호 적합성 미검증”으로 명시한다. 가족 날짜는 일정 메모이고 날씨는 현재 발표의 8시간 범위임을 카드 가까이에 함께 표시한다. 도보 제한을 넘는 후보가 있고 기존 짧은 후보가 한도를 만족하면 그 후보를 우선 제시한다. 후보가 전혀 없으면 한도를 맞췄다고 표현하지 않는다.

**제출 전 필수:** 적어도 남은 시간·도보 상한·날씨 중 핵심 조건 변경이 실제 미션 선택 또는 권고 결과를 바꾸는 사례를 시연한다. 결과가 바뀌지 않는 선호 입력은 그 이유와 적용 범위를 표시한다. 날짜별 예보가 없는 방문일을 검증 완료라고 말하지 않는다.

**후순위:** 음식 알레르기 자동 판정, 군 식단 연동, 전 구간 보행·휠체어 경로, 자동 장소 대체 편집기. 기존 후보 간 선택과 명확한 범위 안내가 먼저다.

## 5. 준비 기록이 여행 기록으로 바뀌고 엉뚱한 일정에 붙을 수 있다

**현재 근거:** 내 여행은 `stamps.length`가 0인지로 계획과 여행 기록을 나눈다. 레이더 준비 체크 완료는 `passport-app.tsx:1781` 부근에서 현재 관련 미션이 아닌 `entries[0]`에 휴가 씨앗을 추가한다.

**실사용 문제:** 현충시설 방문 전 확인 준비만 끝냈는데 계획이 여행 기록으로 이동하고 5군의 방문 기록 수도 늘어난다. 저장 목록 첫 항목이 다른 지역·다른 미션이면 준비 기록의 대상도 어긋난다. 자기 기록과 공적 인증을 구분하는 문구만으로 이 대상·상태 오류가 해결되지는 않는다.

**이번 최소 보완:** 준비 스탬프와 실제 방문 단계 스탬프를 구분한다. 휴가 씨앗만 있는 항목은 계획/준비로 유지한다. 씨앗을 붙일 계획을 사용자가 선택하게 하거나 현재 선택 계획을 명시해 확인한다. 연결할 계획이 없으면 적절한 계획을 선택하도록 안내한다. 실제 현충시설 방문·보상 자격을 확인한 것으로 표현하지 않는다.

**제출 전 필수:** 준비 체크만으로 방문 기록 수가 늘지 않고, 선택한 여행에만 씨앗이 붙는다. 저장·준비·방문·복귀 자기 기록을 사용자가 구분할 수 있어야 한다.

**후순위:** GPS 스탬프 인증, 증빙 이미지 업로드, 공식 보상 인증. 사용자 요청상 민감정보 미수집 원칙을 유지한다.

## 이번 보완 범위 제안

| 순서 | 최소 변경 | 완료 판단 |
| --- | --- | --- |
| 1 | 공개 장소 참조 기반 계획 보존과 여행 고유 ID | 새로고침 후 같은 순서, 같은 유형 여행 두 개 구분 |
| 2 | 가족 제안 내용 그대로 검토하고 명시적으로 적용 | 부모·자녀가 같은 두세 장소를 확인 |
| 3 | 관광 근거와 이름 일치, 관문 거점·중복 후보 정리 | 춘천 사례에서 근거 없는 평화 명칭 제거, 5군 정체성 유지 |
| 4 | 선호/날짜 메모의 적용 범위와 도보 대안 명시 | 미적용 조건을 맞춤 결과처럼 표현하지 않음 |
| 5 | 준비 스탬프의 대상·기록 상태 수정 | 씨앗만으로 방문 기록이 늘지 않음 |

이는 다섯 개의 새로운 기능을 개발하는 계획이 아니다. 이미 있는 저장·제안·미션 이름·조건·스탬프 동작의 연결을 보완하는 범위다. 1·2에서 전체 공사 원문 응답을 저장하는 구현을 선택하지 말고 사용자 생성 계획의 허용 필드만 보존한다. 키·정확한 복귀시각·군 정보·원시 응답은 Git 증빙에도 포함하지 않는다.

## 제출 전 확인과 후속 계획

제출 전에는 위 행동들을 실제 배포 브라우저에서 확인하고, 테스트한 브라우저·화면 크기·URL·코드 버전·결과를 기록해야 한다. 성공 화면만이 아니라 데이터 불러오기 실패, 장소 재조회 실패, 권한 해제, 작은 화면에서의 저장·제안 흐름도 확인한다. 실제 iPhone Safari를 실행하지 않았다면 모바일 폭 데스크톱 에뮬레이션 결과와 분리한다. 이 보고서가 다환경 QA 또는 GitHub 기록 작업을 수행한 증거는 아니다.

기능설명서는 “지역별 관광 후보를 공개 데이터로 구성하고, 추정 시간·방문 조건을 확인하며, 같은 브라우저에서 가족 제안과 자기 기록을 체험한다”는 현재 범위로 정리한다. 검증된 대표 미션과 한 번의 완결된 가족 시연을 먼저 준비한다. 실제 교통 ETA, 다중 기기 공유, 장기 예보·숙소 운영까지 포함한 1박 확정 일정, 식단·혜택 자동 매칭은 후순위로 둔다.

`implementation_plan.md`의 초기 스택·디자인·배포 상태와 마일스톤은 과거 계획이고, `design_concept_v2.md`는 구현 시점 설명이다. 제출 자료를 만들기 전 최신 구현과 실제 QA 결과를 기준으로 완료·제한·다음 단계를 다시 맞춰야 한다. 과거 문서의 계획 문장을 현재 검증 완료로 인용하지 않는다.
