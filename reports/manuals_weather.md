## 1. 최신 첨부 문서에서 확인된 중요 변경

단기예보의 API 제공 시각은 발표 후 **10분 이후**다. 과거 예제에서 흔히 쓰는 40분 대기는 이 첨부 문서의 계약이 아니다. 초단기예보는 매시 30분 발표·45분 이후 제공이며, 2026-06-23 11시 이후 강수확률 `POP` 요소가 추가되었다.

단기예보의 연장 예보기간에는 `PCP`, `SNO`, `WSD`가 정성 코드일 수 있다. 값 `3`을 무조건 3mm 또는 3m/s로 파싱하면 안 된다. 1차 구현은 당일 및 다음 날 시연 범위에 집중하고, 긴 예보기간의 자료는 시간 간격·정량/정성 여부를 분리해서 처리한다.

## 2. 요청 계약

가이드의 서비스 URL은 HTTP로 표기되어 있다. 실제 서버 구현은 다음 HTTPS URL을 사용하도록 제안한다. HTTPS 성공 여부는 실제 호출 단계에서 별도 검증해야 한다.

`https://apis.data.go.kr/1360000/VilageFcstInfoService_2.0`

| 메서드 | 용도 | 서비스 이용 |
| --- | --- | --- |
| `getVilageFcst` | 단기예보 | 당일 2·4·8시간 및 다음 날 일정의 기본 소스 |
| `getUltraSrtFcst` | 초단기예보 | 앞으로 6시간의 비·바람 예보 보완 |
| `getUltraSrtNcst` | 초단기실황 | 현재 조건 카드의 보조 정보; 미래 일정 예보로 사용하지 않음 |
| `getFcstVersion` | 예보버전 | 필요할 때 캐시 변경 여부 확인; 초기 필수는 아님 |

앞의 3개 메서드의 공통 요청은 다음과 같다.

| 파라미터 | 값·형식 | 주의 |
| --- | --- | --- |
| `serviceKey` | 서버 환경변수 `DATA_GO_KR_SERVICE_KEY` | 브라우저·응답·로그에 노출하지 않음 |
| `pageNo` | `1`부터 | 전체 응답 페이지 수를 확인 |
| `numOfRows` | 필요한 최대 개수 | 단기예보는 초기 1000 제안, `totalCount`가 크면 후속 페이지 조회 |
| `dataType` | `JSON` | TourAPI의 `_type=json`과 다른 계약 |
| `base_date` | `YYYYMMDD` | 발표일; 예보 대상 날짜가 아님 |
| `base_time` | `HHmm` | 발표시각; 현재 임의 시각을 넣지 않음 |
| `nx`, `ny` | 정수 격자 X/Y | 경도·위도를 그대로 전달하지 않음 |

`getFcstVersion`은 `base_date/base_time/nx/ny` 대신 `ftype`, `basedatetime`을 사용한다. 가이드의 예시 `ftype=ODAM`은 실황 버전 확인이다. 초기 구현에서 이 메서드가 없어도 예보 조회가 가능하다.

키는 URL 인코딩된 키와 디코딩 키를 구별하여 한 번만 URL 인코딩되도록 한다. URLSearchParams에 넣기 전 필요하면 `decodeURIComponent`를 한 번 적용하되 디코딩 오류는 원문값 유지로 처리한다. 전체 URL이나 fetch 오류 객체를 그대로 로깅하지 않는다. 호출 로그에는 메서드·격자·발표시각·HTTP 상태·정제된 제공기관 오류코드만 남긴다.

## 3. 발표시각 선택과 한국 시각 처리

| 자료 | 발표 `base_time` | API 제공 시각 | 선택 방법 |
| --- | --- | --- | --- |
| 단기예보 | 0200, 0500, 0800, 1100, 1400, 1700, 2000, 2300 | 각각 02:10, 05:10, 08:10, 11:10, 14:10, 17:10, 20:10, 23:10 이후 | 제공시각이 현재보다 지난 가장 최근 발표 |
| 초단기예보 | 매시 HH30 | 매시 HH45 이후 | 45분 전이면 이전 시각 HH30 선택 |
| 초단기실황 | 매시 HH00 | 매시 HH10 이후 | 10분 전이면 이전 시각 HH00 선택 |

가이드는 실황과 초단기예보 일부 요소가 10분마다 갱신된다고 설명한다. 동일 발표를 항상 불변 데이터로 가정하지 않는다. 실황은 기상 관측 기반의 대표값, 초단기/단기는 예보라는 구분도 유지한다.

서버가 UTC로 실행되어도 발표일·발표시각 선택은 반드시 `Asia/Seoul`로 계산한다. 현재 서버의 로컬 시간대나 UTC 날짜의 `slice(0,10)`를 사용하면 한국 자정 부근에서 날짜가 틀린다. `YYYYMMDD`+`HHmm`를 날짜로 변환할 때 명시적인 `+09:00` 오프셋을 사용한다.

경계 예:

- 2026-09-07 02:09 KST → 단기 `20260906/2300`.
- 2026-09-07 02:10 KST → 단기 `20260907/0200` 후보. 실제 자료가 아직 없으면 직전 발표로 한 번 대체한다.
- 2026-09-07 00:44 KST → 초단기예보 `20260906/2330`.
- 2026-09-07 00:45 KST → 초단기예보 `20260907/0030` 후보.
- 2026-09-07 00:09 KST → 초단기실황 `20260906/2300`.

제공시각 직후 지연에 대비하여 구현에서 1~2분의 운영 여유를 둘 수 있다. 이 여유는 서비스가 자체 적용한 정책이며 가이드에 적힌 공식 제공시각과 분리해 기록한다.

현재부터 미션의 공개 거점 도착까지 겹치는 예보 시각들을 평가한다. 단일 현재 날씨를 8시간 또는 1박2일 전체로 복사하지 않는다. `fcstDate/fcstTime` 기준 시계열을 생성하고, 현재 시간대와 마지막 이동 시간대를 포함하는 자료의 범위를 확인한다. 예보가 미션 끝까지 없으면 미확보 구간을 표시한다.

머리글 `F:G`가 격자 X/Y이고 `N:O`가 소수 경도/위도다. 구분값과 1·2·3단계 행정구역을 함께 사용해 강원의 고성군을 선택한다. 경남 고성군과 이름만으로 결합하지 않는다.

첫 시연은 이 대표 격자로 호출할 수 있으나 “철원군 대표 격자 예보”처럼 범위를 표시한다. 실제 장소 기반 보정은 공개 관광 장소의 좌표를 각각 변환해 중복 격자를 합친 뒤 호출한다. 사용자의 실제 위치나 부대 좌표를 요구할 필요가 없다. 공개 만남 거점과 2~4개 장소의 격자만 있으면 된다.

### 공식 좌표변환

첨부 가이드는 Lambert Conformal Conic Projection 소스를 제공한다. 파라미터는 다음과 같다.

- 지구반경 `Re=6371.00877 km`
- 격자간격 `grid=5.0 km`
- 표준위도 `slat1=30°`, `slat2=60°`
- 기준 경도 `olon=126°`, 기준 위도 `olat=38°`
- 소스 내부 원점 `xo=210/5=42`, `yo=675/5=135`
- 마지막 1부터 시작하는 격자 변환은 `floor(x + 1.5)`, `floor(y + 1.5)`이다. 널리 쓰이는 `XO=43, YO=136`과 `floor(value+0.5)` 조합으로 구현해도 같은 양수 격자 결과다. 두 방식의 보정을 섞어 한 칸 더하지 않는다.

계산식의 각도는 라디안으로 바꾼다. `r=Re/grid`, `φ1=30°`, `φ2=60°`, `φ0=38°`, `λ0=126°`일 때:

1. `n = log(cos φ1 / cos φ2) / log(tan(π/4+φ2/2) / tan(π/4+φ1/2))`
2. `F = tan(π/4+φ1/2)^n × cos φ1 / n`
3. `ρ0 = rF / tan(π/4+φ0/2)^n`
4. 대상 위경도 `(φ,λ)`에 대해 `ρ = rF / tan(π/4+φ/2)^n`, `θ = n(λ−λ0)`; 경도차는 먼저 −π~π로 정규화한다.
5. `nx = floor(ρ sin θ + 42 + 1.5)`
6. `ny = floor(ρ0 − ρ cos θ + 135 + 1.5)`

가이드 예제 경도 `126.929810`, 위도 `37.488201` → **nx=59, ny=125**를 위 공식으로 재현했다. 기준점 126°,38°는 **43,136**이다. 원본 소스의 `map_conv` 인수 주석은 0/1 설명이 본문 분기와 반대로 적혀 있으므로 주석보다 실제 분기와 입출력 예제를 따른다.

가이드 격자 범위는 X 1~149, Y 1~253이며 남한 영역만 제공한다고 설명한다. 범위 내라는 사실만으로 해당 격자에 모든 기상 요소가 있다고 확언하지 않는다. 누락·비유한 좌표는 대표 격자 사용 여부를 명시하거나 조회를 보류한다.

## 5. 응답 구조와 필수 요소

정상 응답은 `response.header.resultCode/resultMsg`와 `response.body.items.item`, `totalCount`, `numOfRows`, `pageNo` 구조다. `item`은 배열 또는 단일 객체일 수 있으므로 정규화한다. HTTP 200만 보고 성공으로 처리하지 않는다. 가이드 오류표의 정상값은 `00`, XML 예시는 `0`이므로 문자열화 후 둘 다 허용하도록 한다.

예보 레코드에는 `baseDate`, `baseTime`, `category`, `fcstDate`, `fcstTime`, `fcstValue`, `nx`, `ny`가 있다. 실황 레코드는 `obsrValue`를 사용하며 예보 대상 시각 필드는 없다. `baseDate/baseTime`은 발표 시각이고 `fcstDate/fcstTime`은 대상 시각이다.

| 요소 | 용도 | 값 처리 |
| --- | --- | --- |
| `PTY` | 강수형태 | 단기: 0 없음, 1 비, 2 비/눈, 3 눈, 4 소나기. 초단기에는 5 빗방울, 6 빗방울/눈날림, 7 눈날림 추가 |
| `POP` | 강수확률 | % 값. 미수신과 0%를 구분 |
| `WSD` | 풍속 | 가까운 예보기간은 m/s. 연장 구간은 정성 코드일 수 있음 |
| `PCP` | 단기 1시간 강수량 | `1mm 미만`, `6.2mm`, `30.0~50.0mm`, `50.0mm 이상` 등 범주 문자열을 보존 |
| `RN1` | 초단기 강수량 | 실황은 mm 수치, 초단기예보는 범주 문자열 |
| `TMP` / `T1H` | 기온 | 단기 TMP, 초단기 T1H; ℃ |
| `SKY` | 하늘상태 | 1 맑음, 3 구름많음, 4 흐림. PTY의 무강수와 SKY 맑음을 혼동하지 않음 |
| `LGT` | 초단기 낙뢰 | 자료가 확보되면 야외 주의 이유로 사용; 0/누락 구분 |

### 결측과 범주값

- 숫자 **+900 이상 또는 −900 이하**는 Missing이다. `Number('')=0`, `Number(null)=0`을 그대로 사용하지 않는다.
- 항목이 없는 것, 전송 실패, 빈 응답, `null`인 일반 관측값은 `unknown`이다.
- 가이드는 **강수량/적설 범주표에 한해** `-`, `null`, `0`을 강수없음/적설없음으로 정의한다. 정상 레코드에서 해당 요소의 표현값으로 수신한 경우에만 적용한다. 레코드 자체가 없거나 수신 실패한 것을 무강수로 만들지 않는다.
- `PCP/RN1`은 원문 범주 문자열과 숫자/범위 파싱 상태를 함께 보관한다. 파싱 실패를 0mm로 치환하지 않는다.
- 해상 격자는 기온·강수확률·강수량/적설·습도가 마스킹될 수 있다고 명시되어 있다. 고성·속초 해안 장소에서 부분 결측이 발생하면 남은 요소만 표시하고 결측 요소를 따로 드러낸다.
- 장기 연장 정성 코드의 `WSD=1` 설명은 원문에 “4m/s 이상의 약한 바람”이라고 되어 있어 같은 표의 코드2(4~9m/s)와 겹친다. 이 문서의 오기로 보이는 부분을 임의 수정한 공식 기준으로 인용하지 않는다. 초기 구현은 연장 정성 풍속을 `약한/약간 강한/강한 바람` 문자열로만 표시하고 m/s로 환산하지 않는다.

## 6. 오류·지연·캐시

| 제공기관 코드 | 의미 | 앱 동작 |
| --- | --- | --- |
| 00 또는 0 | 정상 | body·필수 필드·격자·대상시각도 검증 |
| 03 | NODATA_ERROR | 발표 직후라면 직전 발표로 1회 대체; 자료 없음 표시 |
| 01, 02, 04, 05 | 앱·DB·HTTP·연결 오류 | 제한된 재시도 또는 마지막 성공 스냅샷 |
| 10, 11 | 파라미터 오류·필수값 누락 | 자동 재시도하지 말고 내부 검증 오류로 기록 |
| 12 | 서비스 없음/폐기 | endpoint 계약 점검 |
| 20, 21 | 접근 거부·키 일시 제한 | 키 권한 확인 필요. 사용자 화면에 키 자체 노출 금지 |
| 22 | 호출 한도 초과 | 캐시 사용, 즉시 연속 재시도 금지 |
| 30, 31 | 미등록·만료 키 | 설정 확인 필요 |
| 32, 33 | IP 미등록·서명 오류 | 서버 설정 점검 |
| 99 | 기타 | 예보 확인 실패, 정제 코드 기록 |

인증 오류는 JSON 요청에도 XML 또는 다른 형식으로 돌아올 가능성에 대비한다. 비JSON 응답을 그대로 사용자에게 반환하지 않고 `NON_JSON_RESPONSE`와 안전한 상태 문구로 변환한다. fetch 예외 메시지에 serviceKey가 들어갈 수 있으므로 전체 오류 객체도 반환하지 않는다.

초기 정책 제안은 요청 제한 9초, 격자+메서드+발표시각 단위 서버 캐시, 약 10분 간격 갱신이다. 이는 기상청이 요구한 캐시 정책이 아니라 앱의 부하·시연 안정성 선택이다. 마지막 성공 스냅샷을 표시할 때 기존 발표시각·대상시각·수신시각을 유지하고 상태를 `cached` 또는 `stale`로 표시한다. 지나간 예보를 `live`라고 다시 이름 붙이지 않는다.

## 7. 복귀시계와 연결할 최소 구현

우선 `getVilageFcst` 한 메서드로 당일과 다음 날 예보를 확보한다. 다음 단계에서 초단기예보를 연결해 가까운 6시간만 더 최근 발표로 대체할 수 있다. 한 메서드의 현재 실황만으로 앞으로의 미션을 보정하는 방식은 피한다.

최소 응답 모델 제안:

- `status`: live / cached / stale / unknown
- `provider`: 기상청
- `method`, `grid`, `scope`: 공개 장소 격자 또는 시군 대표 격자
- `baseDate`, `baseTime`, `issuedAtKst`, `fetchedAt`
- `coveredFrom`, `coveredUntil`, `coverageComplete`
- `hours`: 대상시각별 PTY·POP·WSD·강수범주·기온 및 요소별 missing
- `risk`: rain / snow / wind / none_detected / unknown, 복수 위험 허용
- `reasons`, `qualityFlags`, `errorCode`

이 모델에는 API키·완성 호출 URL·군 정보·개인 위치가 없다. `none_detected`는 “확보한 예보 요소에서 선택 위험이 나타나지 않음”이지 일반적인 안전 보증이 아니다. 강수 0만 확보했는데 바람이 누락된 경우 전체 risk를 none_detected로 종결하지 않는다.

위험 기준은 기상청의 특보 기준과 구분한 **앱의 여행 계획 정책**으로 관리한다.

| 입력 | 최소 동작 제안 |
| --- | --- |
| 미션 시간대 중 PTY에 비·소나기·빗방울 | 비 예보를 이유로 실내 후보 우선, 날씨 여유 25분 제안 |
| PTY는 없음이나 POP 최대 60% 이상 | “비 가능성”으로 안내하고 실내 대안 준비. 60%는 앱 기준 |
| PTY 눈·비/눈·눈날림 | 야외 미션 주의/비추천 및 운영 확인. 비 버퍼만 적용해 해결된 것으로 표시하지 않음 |
| 정량 WSD 최대 9m/s 이상 | 바람 주의, 야외·해안·케이블카 조건 확인, 여유 35분 제안. 9m/s는 이 앱의 계획 기준이며 강풍특보 판정이 아님 |
| 비·바람이 동시에 해당 | 두 이유를 보존하고 초기에는 날씨 버퍼 max(25,35)=35분. 이것이 실제 이동 지연 예측이라는 표현 금지 |
| PTY/POP/WSD가 부족하거나 미션 끝 시각 미포함 | 날씨 확인 필요. 가상 맑음으로 변환하지 않음 |

25/35분은 기존 시연 보정값을 실제 예보 조건에 연결하기 위한 초기 정책 제안이다. 실제 교통지연 회귀모형이 아니다. 날씨 API의 역할은 공공데이터로 위험 이유와 실내 대안을 선택하는 데 있으며, 데이터 출처가 들어왔다는 이유로 안전마진 자체가 실측값이 되지는 않는다.

시나리오 UI를 유지한다면 `예보 적용`과 `날씨 시뮬레이션`을 명시적으로 분리한다. 사용자가 비 시뮬레이션을 선택하면 live 기상 자료를 변경하거나 해당 예보로 저장하지 않는다. 화면과 데이터 출처에는 어느 모드로 산식이 계산됐는지 표시한다.

## 8. 구현 시 우선 검증할 계약 경계

1. UTC 서버에서 KST 00:09/00:45/02:09/02:10의 base 날짜·시각.
2. 날짜가 바뀐 `fcstDate`, `fcstTime` 결합과 1박 미션 예보 범위.
3. 코드 `00`, 숫자/문자열 `0`, HTTP 200 안의 `03`/`30`.
4. `item` 단일 객체·배열·없음, `totalCount`와 페이지 수.
5. PTY `0`과 누락 구분, +900/−900 missing, 빈 문자열 숫자화 방지.
6. PCP `강수없음`, `1mm 미만`, `30.0~50.0mm`, 숫자형 원문과 parse 실패.
7. 단기 정성 WSD `3`을 3m/s로 오인하지 않음.
8. 변환 예제 126.929810/37.488201 → 59/125, 원점 126/38 → 43/136.
9. 강원 고성 대표격자 85/145와 경남 고성 혼동 방지.
10. 최신 발표 NODATA 후 이전 발표 응답을 반환할 때 발표시각·cache 상태 보존.
11. 실황만 또는 부분 예보만 확보되면 전체 미션을 실제 예보로 검증했다고 표시하지 않음.
12. API키·전체 URL·원시 오류 객체가 응답·콘솔·서버 로그에 포함되지 않음.
