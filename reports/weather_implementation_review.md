# 기상청 예보 구현 수정 확인

- 검토일: 2026-09-07
- 대상: `web/lib/weather.ts`, `web/components/weather-card.tsx`, `web/lib/domain.ts`의 날씨 판정
- 기준: 첨부 `기상청41_단기예보 조회서비스_오픈API활용가이드_2607.zip` 안 260623 DOCX 및 2607 격자표. 계약 정리는 `reports/manuals_weather.md` 참조.
- 방법: 초기 검토 후 루트의 수정 소스를 다시 읽고 첨부 계약과 대조했다. 검토자는 web 코드 수정·실행 테스트·브라우저 조작·API 호출을 하지 않았다.
- 결과: 초기 핵심 결함 3개와 NaN 날짜 방어가 소스에 반영된 것을 확인했다. 이는 정적 수정 확인이며 실제 기상청 인증 호출 성공이나 런타임 테스트 통과의 증거가 아니다.

## 초기 결함과 수정 확인 결과

### 1. null과 잘못된 날짜가 예보값에 섞이는 문제 — 수정 확인

초기에는 `Number(null)=0`이 PTY·POP·WSD의 정상값으로 누적되어 무강수·무풍으로 판정될 수 있었다. 현재 `row.fcstValue == null` 검사가 슬롯 누적 전에 실행되고, 타입에도 null이 포함되었다. 빈 문자열·비유한 숫자·절댓값 900 이상 결측도 함께 제외한다. 따라서 지적한 null→0 누적 경로는 소스상 차단됐다.

가이드의 null→강수없음 예외는 PCP/RN1 같은 강수량 범주 표현에 관한 것이며, 일반 기상요소에 적용하지 않는 현재 방향이 맞다. 초기 8시간 위험 판정에서 강수량 문자열은 수치로 사용하지 않는다.

`Date.parse()` 결과에 `Number.isFinite(ms)` 검사가 추가됐다. 초기 NaN 날짜가 범위 비교를 통과하던 경로도 차단됐다. 현재 시각 이하 및 8시간 이후 레코드도 제외한다.

### 2. 부분 자료를 8시간 전체처럼 표시하는 문제 — 수정 확인

초기에는 한 시간 또는 서로 다른 시간대의 일부 POP·PTY·WSD만 있어도 `clear`로 판정했다. 현재는 다음 정시부터 8개 예상 시각을 만들고 각 시각에 POP·PTY·WSD가 모두 있는지 검사한다. 누락 시각은 `missingTimes`, 전체 확보 여부는 `coverageComplete`로 반환한다. 위험 신호가 없을 때 `clear`는 `coverageComplete=true`인 경우에만 선택된다. 부분 자료에서 관측된 비·바람·눈 신호는 계속 보존한다.

카드는 완전 수신 시 “향후 8시간”, 불완전할 때 “수신한 시간대” 최대값으로 구분한다. 불완전한 시간대 개수와 “날씨가 괜찮다고 판단할 수 없습니다” 안내도 추가됐다. API 연결 성공을 뜻하는 `mode=live`와 예보 범위의 완결성이 별도 필드로 구분된다.

### 3. 눈·비와 눈을 rain으로 축소하는 문제 — 수정 확인

초기 PTY>0 분기는 비/눈(2)과 눈(3)을 일반 비로 축소했다. 현재 각 시간대에서 PTY=2 또는 3이 하나라도 있는지 `some`으로 먼저 확인하고 `snow` 상태를 최우선 반환한다. 소나기(4)가 함께 있어도 눈 신호가 사라지지 않는다.

`Settings.weather`에 snow가 추가되었고 `assess`에서 자체 추정 여유 45분을 적용한다. snow와 wind 조건에서 `실내` 미션을 제외한 미션은 `avoid`로 판정하므로 단순 버퍼만 늘린 뒤 야외 미션을 안전권에 두지 않는다. 엔진 이유에 눈·비눈 예보와 결빙·도로 통제 확인을 추가했고, 카드에도 눈·혼합강수와 결빙·도로 통제 안내가 표시된다. 45분은 앱 추정 정책이며 실제 지연 예측이나 공식 기상 기준은 아니다.

현재 `precipitationType` 반환값은 여전히 최대 PTY 숫자다. 다만 이번 수정의 조건 판정은 별도 눈 존재 검사로 보호된다. 향후 이 반환 필드를 상세 날씨 설명에 사용한다면 형태 집합 또는 시간별 코드로 바꾸어 의미를 보존해야 한다.

## 계약과 일치하는 부분

- base endpoint, `dataType=JSON`, 발표일/발표시각/nx/ny 요청 키가 첨부 계약과 일치한다.
- 7개 시군 대표 격자는 제공 XLSX와 일치한다.
- `weatherBase`의 UTC+9시간−11분 계산은 공식 :10 제공에 자체 1분 여유를 둔 방식이다. KST 자정과 첫 02시 발표 전에는 전날 23시 발표를 선택하므로 계약상 문제를 찾지 못했다. 주석이나 운영 기록에는 1분 여유가 자체 정책임을 남기면 좋다.
- +900 이상/−900 이하 숫자 결측을 거르는 조건은 첨부와 일치한다.
- 현재 유한한 대상시각을 검증한 뒤 지금부터 8시간 범위만 사용하므로 정상 계약 응답의 연장 구간 정성 WSD/PCP를 제외한다. 이 확인은 8시간 범위에 한정한다. 예보 범위를 향후 3~5일로 늘리면 정성코드와 정량값을 별도 파싱해야 한다.
- 풍속 8m/s와 강수확률 60%를 앱 기준으로 표시하며 기상특보가 아니라고 설명한다. 8m/s는 앱의 자체 선택이므로 첨부의 정성 코드 경계와 같을 필요는 없다.
- API 키는 서버 호출 URL 내부에만 들어가고 반환 객체에는 들어가지 않는다. 지정된 두 파일에서는 직접적인 키 출력 동작을 찾지 못했다. 서버 전체 로그·라우트·환경변수 배포는 이 검토 범위 밖이다.

## 남은 범위와 후속 보완

정상 응답의 `item`이 단일 객체로 오면 현재 배열 단언이 런타임 반복 오류를 만들 수 있으므로 배열/단일/없음을 정규화하면 안정성이 좋아진다. SKY를 읽지 않은 `clear`는 “맑음”으로 해석하지 않아야 한다. 강수·바람 기준 미해당을 “날씨 보정 없음”으로 표현하면 확보한 근거 범위를 유지할 수 있다.

카드는 새 요청·권역 변경 때 화면의 예보를 비우고 abort를 사용해 이전 권역 응답이 늦게 들어오는 경합을 막는다. `onApply`는 weather enum만 전달한다. 현재 엔진은 “선택한 날씨 조건의 추정 버퍼 적용 · 현지 기상은 별도 확인”으로 처리하므로 실측 이동시간으로 표현하지 않는다. 앞으로 지속적인 실제 예보 적용 상태를 제공하려면 격자·발표시각·유효범위를 함께 보존해야 한다.

실내 미션은 아직 이름·분류 기반 후보이고 엔진이 미검증이라고 명시한다. snow 상황에서 실내 관광을 제안하더라도 실제 도로 결빙·통제까지 해소됐다는 의미는 아니다.

실제 기상청 키 승인 여부, 인증 요청 성공, provider 응답의 현장 형태, 배포 서버 네트워크, 런타임 경계 테스트는 이 읽기 전용 수정 확인에 포함되지 않는다. 위 3개 수정의 소스 반영 확인을 전체 연동 성공으로 해석하면 안 된다.
